# church-translator

Живой голосовой перевод для церкви: вход с микшера в звуковую карту, обработка,
отдельный физический выходной канал на язык → FM-передатчик → приёмник с
наушником у слушателя. Без сайта, без телефона в руках у слушателя.

Полный технический и бизнес-разбор — в отчёте
[«Синхроперевод для церквей»](https://claude.ai/code/artifact/7c37bf2c-6264-4ffb-bfe5-1a7e40dd5fc5).
Этот репозиторий реализует раздел §09 того отчёта («Будка и звуковая карта»).

## Три стадии, три milestone'а

| Режим (`pipeline.mode`) | Что проверяет | Нужны ключи API? |
|---|---|---|
| `passthrough` | Захват и вывод по каналам, маршрутизация, поведение при обрыве — сам аудио-тракт, без перевода | нет |
| `mock` | Форма пайплайна STT→MT→TTS (потоки, тайминги, лог расходов) на фейковых провайдерах | нет |
| `real` | Полный перевод: AssemblyAI (STT) → Claude (MT) → Cartesia (TTS) | да |

Milestone 1 — это `passthrough` и `mock`, оба уже работают и не требуют ключей.
Milestone 2 — включить `real` с настоящими API. Milestone 3 — автоопределение
языка на лету и клонирование голоса поверх той же архитектуры (см. отчёт, §08).

## Быстрый старт

```bash
uv sync --extra providers            # ставит зависимости в .venv
uv run church-translator list-devices   # смотрим, что видит система
cp config.example.yaml config.yaml   # правим device/каналы под своё железо
uv run church-translator run --config config.yaml
```

**Всегда `--extra providers`, даже если сегодня гоняете только `mock`.** Голый
`uv sync` — команда точной синхронизации: всё, чего нет в наборе по умолчанию,
она удаляет. На рабочей установке будки это вычищает assemblyai, anthropic,
cartesia и python-dotenv (проверено `uv sync --dry-run`: «Would uninstall 21
packages»), и `mode: real` перестаёт запускаться. `uv run` безопасен — он
досинхронизирует недостающее, но лишнего не сносит.

В `mode: mock` с любым 2-выходным устройством (даже обычные наушники) сразу
слышно результат: язык на канале 0 — один тон, на канале 1 — другой. Это и
есть весь smoke-тест на этом этапе — до перевода дело ещё не доходит,
проверяется только то, что каждый язык действительно идёт в свой физический
канал.

## Подключение к реальной звуковой карте

1. `list-devices` — найдите вашу карту в списке. **Если один и тот же прибор
   показан двумя строчками** (одна с `in=N out=0`, другая `in=0 out=N`) — это
   нормально для части USB-устройств: macOS видит вход и выход как разные
   CoreAudio-устройства. Поэтому в конфиге `input_device` и `output_device`
   разнесены — можно указать одну и ту же подстроку в оба поля, код сам
   найдёт нужную половину по наличию каналов.
2. `audio.input_channel` — какой канал на вход несёт сигнал с AUX/direct out
   микшера.
3. Для каждого языка — свой `output_channel`, дальше физически в свой
   FM-передатчик.

### source_languages vs. languages

Два разных списка в конфиге, не путать: `source_languages` — то, что реально
говорит спикер (идёт в STT как candidate list); `languages` — то, во что
переводим на выходе (MT + TTS + канал). Для сценария «спикер говорит по-английски,
слушатели получают русский и украинский» это `source_languages: [en]` и
`languages: [ru, uk]` — не одно и то же множество. Смешивать их нельзя не
только логически: live-тестом 19.08.2026 подтверждено, что AssemblyAI
streaming вообще не принимает `uk` как source (код ошибки 3006), хотя как
выходной язык у Cartesia TTS украинский работает нормально.

### Реальная связка: Behringer X32 → Focusrite Scarlett 2i2 → 2 FM-передатчика

Готовый конфиг под это железо — `config.church.example.yaml`. Коротко про его
ограничения (подробнее — комментарии внутри файла и отчёт §09):

- **2i2 = 2 выхода = потолок 2 языка.** Больше — либо Aggregate Device из
  двух интерфейсов (Audio MIDI Setup), либо интерфейс побольше.
- **Вход сейчас — copy of Main L/R с X32**, то есть весь общий микс, а не
  изолированный микрофон спикера. Работает, но для точности STT в Milestone 2
  лучше развести отдельную AUX-шину только с речью.

## Milestone 2: реальные провайдеры

```bash
uv sync --extra providers
cp .env.example .env   # впишите ASSEMBLYAI_API_KEY / ANTHROPIC_API_KEY / CARTESIA_API_KEY
```

Все три провайдера сверены с реально установленными SDK (не с документацией
"на глаз") и прогнаны с настоящими ключами:

- **Cartesia (`cartesia_tts.py`)** — подтверждено живым вызовом, отдаёт
  настоящее аудио.
- **AssemblyAI (`assemblyai_stt.py`)** — подключение и авторизация проходят;
  полный прогон с речью — когда будете тестировать на живом звуке.
- **Claude (`claude_mt.py`)** — проверено полным циклом: реальная фраза,
  распознанная (с шумом) через AssemblyAI, переведена корректно и осмысленно
  несмотря на ошибки в расшифровке — LLM-перевод неплохо переживает шумный
  вход, это не хрупкий rule-based переводчик.

**Живая находка 2026-08-19:** полностью открытое автоопределение языка
(`language_detection=True`, без подсказки) один раз дало третий, случайный
язык на неоднозначном звуке. С `language_codes=["ru","en"]` (список того, что
церковь реально ожидает) — не повторилось. `cli.py` теперь всегда передаёт
языки из конфига в STT как candidate list, а не оставляет распознавание
полностью открытым.

Если в будущем SDK у любого из провайдеров поменяются — контракт
(`STTProvider`/`MTProvider`/`TTSProvider` из `providers/base.py`), который
использует `pipeline.py`, трогать не нужно, меняется только код внутри
конкретного файла провайдера.

Что бы вы ни поменяли в этих трёх файлах — `voice_id` должен оставаться
**одним и тем же на весь сеанс службы для каждого языка**. Это и есть
архитектурный фикс жалобы «голос плывёт» из отчёта §04.1 — если TTS-вызов
внутри `synthesize()` не получает один и тот же `voice_id` каждый раз,
проблема вернётся.

## Учёт расходов

Каждый вызов STT/MT/TTS пишет строку в `logs/usage.csv` (компонент, язык,
длительность/символы, время) — see отчёт §06. Ничего дополнительно включать
не нужно, логирование уже внутри `pipeline.py`.

## Чек-лист первого теста в церкви

**На пустом зале, без прихожан** — первый прогон живой физической цепи не
должен совпадать с первым разом перед аудиторией.

1. Подключить Scarlett 2i2 к Mac по USB.
2. `uv run church-translator list-devices` — найти реальное имя интерфейса
   в списке (может не совпасть буква в букву с «Scarlett 2i2»).
3. `cp config.church.example.yaml config.yaml`, свериться, что
   `input_device` / `output_device` совпадает с тем, что реально показал
   `list-devices`.
4. Завести X32 AUX/direct out в L/R входы Scarlett; выходы Scarlett — в два
   FM-передатчика (L → передатчик 1, R → передатчик 2).
5. **Первый прогон — `pipeline.mode: mock`, не `real`.** Взять два
   приёмника, слушать в наушниках, говорить/играть звук через X32 — на
   приёмнике 1 должен быть слышен один тон, на приёмнике 2 — другой. Это
   проверка чистой физики (маршрутизация каналов), без API и без риска.
6. Только если маршрутизация подтвердилась — переключить на
   `pipeline.mode: real` и повторить: сказать фразу по-английски в микрофон,
   через ~1–2 секунды на приёмнике 1 должен звучать перевод на русском,
   на приёмнике 2 — на украинском.
7. Следить за терминалом на `input overflow` / `output underrun` —
   если появятся регулярно (не разово), это сигнал подвинуть `blocksize`
   в конфиге, а не игнорировать.

## Приложение для будки (menu bar app)

```bash
uv run church-translator-app
```

Иконка 🎙️ в строке меню (не в Dock — это утилита для будки, не оконное
приложение). Всё то же, что `run` в терминале, но без него: те же
`AudioRouter`/`Pipeline` вызываются напрямую внутри процесса, поэтому
старт/стоп — просто клик, без проблем с сигналами, что дважды ловил на
подходе через `uv run` в терминале.

- **▶️/⏹** — старт/стоп перевода.
- **Тестовый режим (mock)** — переключатель `pipeline.mode` mock/real, задизейблен, пока перевод идёт.
- **Входное/выходное устройство, входной канал, каналы языков** — реальный список устройств с этого Mac, галочка на выбранном; клик меняет и сразу сохраняет `config.yaml`. Если назначить два языка на один канал — код сам поменяет их местами, а не молча даст коллизию.
- **Открыть логи / Открыть debug-аудио** — Finder на нужную папку.

`config.yaml` при этом переписывается программой (комментарии из
`config.church.example.yaml` в нём после первого клика пропадут — это
осознанный компромисс: раз каналы настраиваются из приложения, читать сырой
YAML уже не обязательно).

## Запись образца голоса для клонирования

```bash
uv run church-translator record-sample --config config.yaml --seconds 8 --out pastor_sample.wav
```

Пишет с уже настроенного входного канала. Для клона важнее чистота, чем
удобство — если под рукой только вход "copy of Main L/R" с музыкой, лучше на
эти 8 секунд попросить пастора сказать пару фраз в отдельный чистый
микрофон, а не брать кусок из общего микса. `voices.clone()` в Cartesia
работает и от 5-секундного клипа; полученный `voice_id` дальше идёт в
`languages[].voice_id` в конфиге как обычный голос — озвучка кросс-языковая
"из коробки" (клон с английского клипа спокойно говорит по-русски и
по-украински).

## Что дальше

- Заменить `mode: mock` на `mode: real` с настоящими ключами (Milestone 2).
- Добавить code-switching (модель STT с нативным определением языка на лету
  вместо фиксированного `source_language`) — отчёт §04.2, §08.
- Клонирование голоса спикера — отдельная фаза, требует согласия и
  дисклеймера слушателям (отчёт §07) до того, как включать в проде.
